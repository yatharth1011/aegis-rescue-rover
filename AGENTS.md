# Rules for AI coding agents working on A.E.G.I.S.

Read this whole file before you change anything. It applies to every agent: Antigravity, Gemini, Copilot, Cursor, Claude, any other.
These rules come from mistakes that have already happened in this project.
Task-specific how-tos are in `.agents/skills/*/SKILL.md`. Read the matching one before starting that kind of task.

## 1. The project in one paragraph

A.E.G.I.S. is a small autonomous search-and-rescue rover for a table-top demo (course TL101, IIT Ropar).
- An ESP32-S3 runs the motors, the sensors and the safety reflexes (`team_share/firmware/aegis_s3/`).
- An ESP32-CAM streams video (`team_share/firmware/aegis_cam/`).
- A laptop runs the "edge brain" (`team_share/edge/aegis_edge.py`, reusing `team_share/simulation3d/brain.py`) over Wi-Fi. It does YOLO detection, scream homing, mapping and planning.
- The mechanical design is a Fusion 360 script (`team_share/Build_AEGIS_Rover/Build_AEGIS_Rover.py`).
- Print, laser-cut and guide files are generated by scripts in `team_share/tools/`.
- `team_share/HOW_AEGIS_WORKS.md` explains the whole system in plain language. Read it once.

The design is approved and **the parts are already ordered. Nothing more can be bought.** Only reusable lab items can be added: screwdrivers, a soldering iron, the laser cutter, the 3D printer. Personal phones and laptops are also fine.

## 2. Ask before you do any of these

Stop and ask the user in chat. Describe the change in one or two lines and wait for a clear yes before you:

1. **Change the design.** That means any dimension, hole, part, material, pin assignment, firmware parameter in `aegis_params.h` / `aegis_config.h`, wiring, or the bill of materials.
2. **Add hardware the team does not have.** First check the BOM (`team_share/tools/bom_excel.py`) and the M3 kit contents: 20 × M3x6 screws, 20 nuts, and M-F/F-F pillars of 6/10/15/20 mm (10 of each). There are **no M3x10 screws.**
3. **Delete, rename or move any file or folder.** Also ask before restructuring the repo or "cleaning up".
4. **Rewrite git history, force-push, change repo visibility,** or push anything other than ordinary commits.
5. **Touch the user's own files:**
   - `The Most Final AEGIS Body.f3d` and `The Most Final AEGIS Body Detailed.f3d`. These are the team's own saves from Fusion. Never overwrite them.
   - Anything under `to_submit/`, `course_templates/` or `FINAL/1_submission/`.
6. **Change the structure or layout of a course document** (the deck, approval form or item list). Those follow the course templates exactly.
7. **Anything outside `project/`.** In particular `../TL101_A2/` and `../COURSE/` belong to a separate assignment. Never mix the two.

A bug fix that keeps behaviour, dimensions and interfaces the same does not need asking. Say what you fixed afterwards.

## 3. How to change things

- **Smallest change that solves the problem.** Don't reformat, reorder, rename or "modernise" code you were not asked to touch. Don't add abstraction layers, config systems, classes, type hints or logging frameworks the code doesn't already use.
- **Match the surrounding code.** Use the same naming and the same comment density: short comments that say *why*, never ones that narrate *what*. Keep the same style of module docstring at the top (what it does + the exact command to run it + what it outputs). Keep the same idioms (numpy, plain functions, `os.path`).
- **No placeholder code.** No `TODO: implement`, no `pass`, no mock values left in. If you can't finish something, say so instead of faking it.
- **Edit sources, not outputs.** These are generated; edit their source, then regenerate:

| Output | Source | Regenerate with |
|---|---|---|
| `team_share/AEGIS_*_Guide.pdf`, `AEGIS_How_It_Works.pdf` | `FABRICATION_GUIDE.md`, `edge/README.md`, `HOW_AEGIS_WORKS.md`, `tools/assembly_guide.py`, `tools/wiring_steps.py` | `tools/make_guides_pdf.py`, `tools/assembly_guide.py`, `tools/wiring_steps.py` |
| `FINAL/**` | everything above | `tools/make_final.py` (copies only, never edit FINAL by hand) |
| `print/*.3mf`, `print/*.stl` | Fusion exports in `Build_AEGIS_Rover/output/` + `tools/make_3mf.py` | `tools/make_3mf.py` |
| `Build_AEGIS_Rover/output/lasercad_*.dxf` | Fusion DXF exports + `tools/lasercad_dxf.py` | `tools/lasercad_dxf.py` |
| Fusion model, STEP, STL, renders | `Build_AEGIS_Rover/Build_AEGIS_Rover.py` | Run it **inside Fusion 360** (Utilities → Scripts and Add-Ins). It cannot run from a terminal. |

- **One consistent truth.** If you change a number (a pin, a dimension, a part count, a test result), update every place that states it: code, guides, README, BOM, HOW_AEGIS_WORKS. Then regenerate the PDFs. `grep -rn` for the old value first.

## 4. Verify before you claim

Run the check that matches the change, and report the real output, including failures:

| Changed | Check |
|---|---|
| Firmware core (`components/aegis_core`) | `make -C team_share/firmware/aegis_s3/test/host` (must stay 41/41 or more) |
| Any firmware | `. ~/esp/idf_env.sh && cd team_share/firmware/aegis_s3 && idf.py build` (same for `aegis_cam`) |
| Brain / planning / edge code | Before/after simulator comparison on the **same seeds**; see `.agents/skills/aegis-brain-sim` |
| Edge program wire protocol | `team_share/edge/test_end_to_end.py` against `fake_rover.py` |
| Guides | Open the PDF (or `pdftotext`) and check the page you changed |

Never write "should work", "done" or "tested" for something you didn't run. Quote numbers exactly (e.g. "17/32 vs 20/32, 0 falls"), and don't round them up into something better-sounding.

## 5. Writing style (code comments, guides, README, commit messages)

- Plain, professional and specific. The readers are first-year engineering students.
- **No hype:** no "revolutionary", "cutting-edge", "seamless", "robust solution", "leverage", "🚀", no exclamation marks.
- No emojis anywhere.
- Don't invent credits, titles or roles. Never call anyone "team leader", "lead architect" or similar. Never credit an AI tool as an author or co-engineer.
- **Commit messages:** one plain sentence saying what changed and why. **No `Co-Authored-By` or "Generated with" lines for any AI tool.**
- The user prefers **PDF guides** (well formatted) over Markdown files they have to read. Markdown sources are fine; regenerate the PDF.
- Don't add extra slides, sections, columns or fields to course documents "to be helpful". Course rules come first.

## 6. Privacy: the GitHub repo is public

- **Never commit:**
  - teammates' roll numbers (pattern `2026AIB` + 4 digits; they live only in the git-ignored `team_share/tools/team.json`);
  - personal email addresses;
  - phone numbers;
  - the contents of `to_submit/`, `course_templates/` or `FINAL/1_submission/`.
  `.gitignore` already covers these; don't weaken it.
- Before every push, run:
  ```bash
  git diff --cached | grep -nE "2026[A-Z]{3}[0-9]{4}|@gmail|@iitrpr" || echo clean
  ```
- Commits use the GitHub noreply address that is already configured; don't change `git config user.email`.

## 7. Picking up work another agent started

Different agents take turns on this repo. Before you start:
1. Run `git status --short` and `git log --oneline -10`.
2. If there are uncommitted changes you didn't make, **don't revert, overwrite or "tidy" them.** Ask the user what they are.
3. Read the files you are about to change in full. Don't patch from a guess of what they contain.

When you finish:
- Leave the work committed, or tell the user exactly which files are changed and not yet committed.
- Say what is verified and what is not.

## 8. When you are unsure

Ask one short, specific question instead of guessing. A wrong guess costs the team more than the time it takes to answer you.
